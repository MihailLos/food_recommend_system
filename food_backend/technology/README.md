# Модуль технологических экспериментов

Структура для исследования массовой доли сухих веществ. Интерфейс ввода и
импорт Excel пока не реализованы. Каталог продуктов и CPT_To_Products не меняются.

## Таблицы

- `raw_materials_batches`: партия, код, сорт, происхождение, покупка/урожай, хранение.
- `experiment_series`: группировка независимых технологических повторов.
- `experiment_samples`: образцы партии, состояние до/после, дата отбора и источник.
- `technological_experiments`: независимая обработка, массы продукта, параметры,
  ссылки `before_sample_id` и `after_sample_id`.
- `dry_matter_measurements`: отдельные лабораторные определения, номер бюксы,
  m0/m1/m2, сообщённый процент, метод и источник, исключение с обоснованием.
- `drying_weighings`: последовательные взвешивания одной навески после сушки.

Сырой образец можно связать с несколькими обработками той же партии без
копирования измерений. Это общая исходная информация, а не новые независимые
наблюдения. При статистическом анализе и разбиении ML-выборки необходимо
учитывать общие партии и образцы. Дата отбора не заменяет дату анализа.

Масса `initial_product_weight_g` — фактически направленная на тепловую обработку
масса после подготовки и отбора проб. Конечная масса измеряется без упаковки.
Условия стекания/охлаждения записываются в примечании. `foil_used` — признак
способа приготовления, а не включения фольги в массу.

Для моркови 76/77 °C записываются как температура воды при закладке;
`time_start_event` — закладка в нагретую воду. Не считать это постоянной
температурой всей обработки. `NULL` означает отсутствие сведений, а 0 —
известное нулевое значение.

`m0_g` — подготовленная тара, `m1_g` — та же тара с влажной навеской,
`m2_g` — принятая лабораторией конечная масса. Промежуточные массы можно
сохранить в `drying_weighings`; они не заменяют m2 автоматически. Расхождение
между ними требует проверки журнала и метода. Старые проценты без масс
сохраняются в `reported_dry_matter_pct`; массы из процентов не восстанавливать.

## Расчёты

- `v_dry_matter_measurements`: `(m2-m0)/(m1-m0)*100`, исходный сообщённый
  процент и разница в процентных пунктах. Для анализа используются массы,
  если все три доступны, иначе сообщённый процент. Поле `result_source`
  показывает источник: `masses`, `reported`, `missing`.
- `v_sample_dry_matter_summary`: среднее и выборочное SD принятых параллелей,
  число измерений, исключений и результатов, принятых в расчёт. SD при одном
  результате остаётся NULL. Это лабораторный разброс, не разброс между варками.
- `v_experiment_dry_matter_results`: выход и изменение массы, абсолютные массы
  сухих веществ, истинная сохранность и потери. При отсутствии исходного/конечного
  состава или массы соответствующие результаты NULL. При нулевом исходном
  содержании сохранность не определена. Значения выше 100% не обрезаются.

Представления рассчитываются из актуальных данных без округления промежуточных
результатов. История версий расчётов и снимки наборов для публикаций пока не
реализованы. До изменения формул для опубликованных результатов нужны такие
снимки. Автоматического подтверждения методики/допустимости лабораторных
расхождений и статистической проверки нормативов нет.

## Миграция и проверки

`python manage.py migrate technology` применяет атомарную `0001_initial`.
Она заменяет только пустые вручную созданные исследовательские таблицы;
при наличии хотя бы одной записи останавливается. Проверка пустоты выполняется
под блокировками в той же транзакции. DROP не использует CASCADE.
Миграция намеренно не имеет автоматического обратного хода, который мог бы
удалить уже собранные результаты. Файлы SQL 001 и 002 являются частью истории
миграции: дальнейшие изменения оформлять новой миграцией.

План и повторный запуск Django учитывают запись `technology.0001_initial`
в `django_migrations`. На серверной БД миграция уже применена 19.11.2026;
при последующем развёртывании этих исходников повторного пересоздания не будет.
Это приложение использует ссылочную Django-модель с `managed=False`
`ProcessingType` для существующей таблицы `Culinary_Processing_Types`.

Проверки через psql с параметрами подключения из окружения:

```sh
psql -X -v ON_ERROR_STOP=1 -f technology/sql/003_check_integrity.sql
psql -X -v ON_ERROR_STOP=1 -f technology/sql/004_test_calculations.sql
```

Второй скрипт проверяет формулы, общую исходную пробу, отсутствие данных,
исключения, ограничения и защиту связей. Работает внутри BEGIN/ROLLBACK,
использует отрицательные тестовые ID и не расходует значения последовательностей.
Если такой ID/код уже занят, скрипт останавливается, ничего не перезаписывая.
Файлы 001/002 отдельно после миграции запускать не нужно.

Локальная резервная копия исходной пустой схемы:
`backups/technology_before_20261119.sql` от корня репозитория (исключена из git).
Это снимок схемы, не резервная копия всей базы. Восстановление выполнять
сначала в отдельной БД. Для восстановления старой схемы на рабочей БД потребуется
отдельная согласованная миграция с учётом данных, собранных после обновления.
